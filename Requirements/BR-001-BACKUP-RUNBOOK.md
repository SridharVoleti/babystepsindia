# BR-001 — Provider-Native Daily Backup: Policy, Procedure & Evidence

Gap ID `BR1-G01` / Building Block BB-18 / Requirement BR-001.

## Status of this document

This runbook pins the **policy and procedure** BR-001 requires. As of this writing, this
codebase has never been deployed to a real Supabase production project (no project ref, no
`supabase` CLI config, no live traffic — confirmed by the PC-005 processor survey, which found
every external integration point, Supabase included, still a local stand-in). There is therefore
no live dashboard to flip a backup toggle in and no real evidence artifact to capture yet.

**What this document IS**: the pinned policy this project commits to, and the exact one-time
procedure to follow — and the auditable evidence to capture — the moment a real production
Supabase project exists.

**What this document is NOT**: a claim that daily backup is already configured in a production
system. It isn't, because no such system exists yet. Treat the checklist in
["One-time production configuration"](#one-time-production-configuration-do-this-once-a-real-project-exists)
as a blocking pre-launch step, not a completed action.

## Frozen policy (BR-001)

1. **V1 uses simple daily provider-native managed database backup.** Supabase's built-in
   automated daily Postgres backup is the entire backup mechanism. No PITR add-on, no custom
   `pg_dump`/cron backup job, no second backup pipeline of any kind is introduced by this
   codebase — confirmed by `tests/br-001-architecture.test.ts`, which scans the repo for any
   backup/dump/cron tooling and fails if one is ever added.
2. **Git/source control is the recovery source for code, content, and versioned configuration.**
   Every schema change lives in `supabase/migrations/*.sql`, committed to git — schema state is
   always reconstructable from the migration history in this repository, independent of any
   database-level backup. Application code, environment-variable *names* (not secret values),
   and every other versioned artifact this repo tracks recover the same way: `git checkout` of
   the relevant commit.
3. **Derived state is reconstructable, not itself a backup target of primary concern.** Tables
   that are computed/observational copies of other authoritative state can be regenerated by
   re-running the process that built them, rather than depending on point-in-time backup
   precision:
   - `monitoring_job_snapshots` / `monitoring_job_monthly_aggregates` (AN-002) — an explicitly
     observational copy; re-running `syncMonitoringSnapshots` against the still-authoritative
     source job-run tables rebuilds it.
   - `analytics_daily_app` / `analytics_daily_level` — derived aggregates over
     `analytics_contribution_receipts`; re-running `runDailyAggregation` for an activity date
     rebuilds them from the same source contributions.
   - `platform_alerts` — an operational signal, not a system of record; losing history here
     loses visibility into past incidents, not authoritative business state.

   Everything else (accounts, learners, subscriptions, entitlements, support cases, consent
   records, staff identity, etc.) is authoritative and depends on the provider-native backup
   above — there is no secondary copy of authoritative state anywhere in this codebase.
4. **Production backups are never used to seed a dev/test environment.** A production database
   backup/restore artifact must never be loaded into a development, staging, or automated-test
   environment. Local development and CI use the in-memory/on-disk SQLite adapter
   (`src/lib/db/client.ts`) exclusively — there is no code path in this repository that loads a
   Supabase backup file into a non-production database, and none should ever be added.
5. **PC-004 deletion obligations remain authoritative through a restore.** A restored backup can
   resurrect learner data whose erasure had already completed before the backup was taken (the
   backup necessarily predates the erasure). Restoring a backup is not itself sufficient recovery
   — **`replayDeletionObligations` (`src/lib/data-retention/service.ts`) must be run immediately
   after any restore**, before the restored database is exposed to any reader. It re-applies
   every previously-completed erasure receipt idempotently, so a resurrected pre-erasure row is
   re-erased rather than silently reappearing. This function was built specifically as this
   handoff point during PC-004 and has never had another caller — restore is that caller.
6. **Backup/provider failure is surfaced, not silently swallowed.** `POST
   /v1/internal/backup-status` (new in this build) is the integration point for reporting the
   daily backup's own outcome. A `"failed"` report raises a deduplicated `critical` alert via
   AN-003's `raiseDeduplicatedAlert` (`alert_type: "provider_backup_failure"`, capability family
   `critical_providers` — the first real detector for that AN-003 family, which previously had no
   detector wired to it at all); a `"completed"` report resolves it. The exact upstream signal
   source — a provider webhook, or a scheduled status-check script polling the provider's own
   status API — is an infrastructure decision for whenever a real project exists; this endpoint
   and the alert it drives are ready either way, and require no changes on that day.

## One-time production configuration (do this once a real project exists)

This checklist is intentionally manual — it is a production infrastructure action, not something
any code in this repository can perform on its own:

1. In the Supabase project dashboard, under Project Settings → Database → Backups, confirm daily
   automated backups are enabled (this is Supabase's default for paid projects; verify rather
   than assume for the specific plan in use).
2. Record the retention window shown for the current plan in this document (replace this
   placeholder line once verified: *"Retention window: \<pending — record when a production
   project exists\>"*).
3. Do **not** enable a PITR add-on or configure any custom backup schedule — rule 1 above.
4. Wire whatever status-reporting mechanism is chosen (provider webhook or a status-check script)
   to call `POST /v1/internal/backup-status` with a `backup-status-reporter` service assertion on
   both success and failure, so AN-003 alerting has a real signal.
5. Confirm no CI/deploy script anywhere restores a production backup into a non-production
   environment (rule 4) — `tests/br-001-architecture.test.ts` checks this repository's own
   scripts for that pattern, but any manual ops runbook outside this repo should be checked too.

## Restore procedure (once a real project exists)

1. Restore the provider-native daily backup through Supabase's own restore mechanism.
2. **Before exposing the restored database to any reader**, run
   `replayDeletionObligations` (`src/lib/data-retention/service.ts`) against it — rule 5 above.
3. Confirm `monitoring_job_snapshots`/`analytics_daily_*` derived tables are either restored
   alongside the authoritative tables or rebuilt via their own sync/aggregation jobs — rule 3
   above; neither is a substitute for the other being current.
